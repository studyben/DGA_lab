### 1-已修复-[中]-条码报告来源链接丢失条码上下文

- **入口/函数**: TrendsPage 检测结果表格 → 查看来源 → 查看条码报告 → ReportPage。
- **文件(行号)**: frontend/src/features/condition-analysis/TrendsPage.tsx:76；frontend/src/features/laboratory/ReportPage.tsx:33、49、121。
- **输入场景**: 有 laboratory.read 权限的用户在任意趋势结果中点击“查看条码报告”。
- **实际分支**: 链接导航至 `/lab/reports?barcode=<所选结果条码>`；main.tsx 将其路由到 ReportPage，但 ReportPage 以空字符串初始化 barcode，挂载 effect 只管理 mounted/cleanup。
- **预期行为**: 来源导航应保留所选条码，展示该条码报告状态或至少预填条码以供查询。
- **实际行为**: 报告页显示空条码查询表单，未读取 URL 参数，未查询所选报告。用户需要返回趋势页复制条码再手动查询。
- **直接证据**: TrendsPage.tsx:76 仅通过 query 参数传递条码；ReportPage.tsx:33 的 `useState('')`、49–52 的挂载 effect 均未消费该参数；唯一用户查询入口为 121 行 form submit 的 `load(barcode)`。完整报告页没有 URLSearchParams 或 location.search 读取。
- **影响**: 来源追溯主链路局部失效；链接表面上具备条码定位能力，目标页实际上丢弃该上下文。现有新增浏览器测试不点击来源报告链接，因此无法发现此回归。
- **建议改法和验证点**: 由报告页拥有并明确实现 barcode query contract，校验/归一化后预填并加载报告（若修改目标页，需要 controller 记录必要的 S2 文件范围调整）；或将此入口收束到已经支持 barcode 参数的工作台，不承诺未实现的报告定位。浏览器从指定趋势行点击来源后，断言目标条码及对应报告状态；同时保留无 laboratory.read 用户无该入口的验证。
- **修复风险（低/中/高）**: 低；新增自动加载应遵守目标页现有取消和重复挂载规则。
- **严重程度（低/中/高/严重）**: 中（P2）。
- **复审与最终裁决**: accepted → fixed。ReportPage.tsx:33 由 URL 条码初始化输入，49–54 的挂载 effect 归一化并对非空、长度不超过 40 的 sourceBarcode 调用现有 load。计划的 S2 review correction 已明确将 ReportPage.tsx 纳入范围，仅消费条码深链接和读取现有报告接口。
- **取消链复核**: StrictMode 首次 setup 发出请求 A，cleanup 设置 mounted=false 并通过 stopPending 中止 A、清除 timer；第二次 setup 重置 mounted=true 并发出请求 B。A 即使晚到，success/catch/finally 都检查其自身 controller.signal.aborted，无法写入 report/error/busy 或安排 polling。B 正常读取；后续离开页面同样中止当前请求和 timer。自动来源加载只调用既有 GET 路径，没有触发 retry POST，也未改变报告生成、撤回或权限语义。
