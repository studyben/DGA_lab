## Required review lenses

### Architecture boundary review

Pass. AssetImports remains the public command seam; AssetDirectory owns readable identities, tree and sources. New private validator and transaction-bound writer remain inside assets. The writer owns row persistence only; the coordinator owns intent, auth, revision, FileStore verification, batch state, audit and operation success (plan 111–116). This matches frozen D2 and ADR-0004. No asset-to-lab/analysis dependency, shared business import layer or new provider is proposed. Formal UUID and material text identities remain distinct throughout the API, source schema and UI.

### Best-practice review

Pass with execution risks listed below. The plan explicitly includes stale-fact refresh, exact warnings, unknown-response recovery, current-grant linearization, rollback at late writes, safe file bounds, authenticated originals and real migration fixtures. The primary seam is public AssetImports/AssetDirectory with real PostgreSQL; existing SQLAlchemy events/transport wrappers are legitimate failure injection rather than private-table success assertions. HTTP-only tests retain transport/security ownership. Future tests must prove the behaviors, not merely assert helpers were called.

### Optimal-solution review

Pass. Extending the retained v2 coordinator/parser and extracting the existing row writes is a credible smaller path than a parallel import framework or independently committing lifecycle calls. Retaining SITES validation while adding a focused material/equipment validator limits migration of old policy. JSONB staging and existing operation/revision tables already fit the new mode; a new queue, task table or domain repository hierarchy is unnecessary. Typed source target_key is justified by the actual material schema.

### Overengineering review

Pass. The additional controls are tied to frozen current requirements: reserved-prefix references, precise warning confirmation, durable retry outcomes, full duplicate history, current facts and whole publication. One additive migration and two private focused capabilities are proportionate. Renaming private site-only coordinator/parser to v2 ownership is bounded; no generic registry, compatibility engine, distributed transaction, provenance taxonomy or future laboratory abstraction is introduced.

### Overcoupling review and slices

Pass. The three slices describe independently observable behaviors, not separate database/UI/platform foundations: S1 retained staging/review/revision with no business writes; S2 atomic formal publication plus provenance, authorization and failure proof from the first formal write; S3 usable operator chains and exact-capacity/upgrade closeout. S1's temporary publication guard is explicit and must be removed before delivery. S2 necessarily composes masters, equipment, sources and operation completion because atomicity is the work unit's central contract. Deferring frontend completion to S3 does not defer authorization or recovery guarantees at the public mutation boundary. Shared allowlists do not authorize unrelated cleanup or later units.
