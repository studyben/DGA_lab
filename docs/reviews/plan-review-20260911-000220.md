# Plan review — Issue #8 barcode report

## Reviewed target and scope

- Target: `docs/work-units/issue-8/plan.md`
- Scope: database/report state model, laboratory ownership, asynchronous worker recovery, PDF/file delivery, browser acceptance, slice sequencing, and Gateflow readiness.
- Evidence: Issue #8 goal confirmation, `README.md`, `backend/dga/laboratory/workbench.py`, `backend/dga/laboratory/public.py`, `backend/dga/laboratory/http.py`, `backend/dga/shared/files.py`, current migrations, tests, and Compose files.

## Assumptions tested

- A unique current-row model can satisfy “no visible versions” without allowing a stale worker to publish an old PDF.
- Finalization and report snapshot creation can share the existing `Engine.begin()` transaction.
- Report lookup/download can remain inside the laboratory public boundary while reusing the shared file port.
- A database-backed worker can recover after process death without a generic queue.
- The proposed three slices can be implemented without re-deciding schema, method ownership, or test scope.

## Findings

### PR-001-未修复-高-计划未定义可直接实现的 schema 与精确快照契约
- **位置**: “State model and invariants”“Implementation slices / Slice 1”
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: 计划只列出状态、generation/claim token 和 snapshot 的概念字段，未给出表字段、约束、索引、快照 JSON shape、Decimal/时间序列化或旧 finalized 数据处理。
- **反例/失败场景**: 实施时可分别选择把 retry 当成新 generation、把 generation 当 finalization 身份、或依赖 `testing_finalized_at`；这些选择会产生不同的并发语义。迁移到已有本地 finalized 样品时，也可能出现 sample 已定稿但没有 report row 的不可恢复状态。
- **为什么有问题**: Gateflow 要求 plan 不再让 implementation 重新设计 schema/state transitions。当前计划无法唯一决定列与约束，也没有定义 finalized/no-row 的公开结果。
- **直接证据**: 当前 `oil_samples` 只有 `testing_status/testing_finalized_*`；`LaboratoryWorkbench.finalize()` 使用可注入 clock，同一时间戳不能充当可靠 generation identity；当前 migration head 为 0006，数据库中可能已有 finalized 样品。
- **影响**: 生成错误代码 / 状态不一致 / migration 后用户可见死状态 / review 不可验收
- **建议改法和验证点**: 明确 0007 的每一列、check/unique/index；区分 finalization token 与 worker claim token；给出稳定 snapshot v1 JSON shape 与 Decimal/时间编码；明确旧 finalized/no-row 查询和恢复策略；为约束与迁移场景增加 real-PostgreSQL assertions。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-002-未修复-高-下载检查与撤销定稿之间仍存在 TOCTOU 窗口
- **位置**: “Download safety”
- **问题类型**: 并发恢复风险 / 状态机漏洞
- **当前写法**: 应用先重新校验 sample/current generation，再读取对象并返回；未定义数据库锁生命周期。
- **反例/失败场景**: 下载请求读取到 `READY` 后释放事务，另一请求撤销定稿并返回成功，随后第一个请求仍从对象存储取回并发送旧 PDF。这样“撤销后不可访问”并不成立。
- **为什么有问题**: 目标明确要求 withdrawal invalidates old PDF。仅重复查询而没有串行化点不能保证该语义。
- **直接证据**: 当前 `withdraw_finalization()` 对 sample 使用 `FOR UPDATE`；计划的 `read_report_file` 没有说明是否在对象读取/校验期间保持相容锁。
- **影响**: 已撤销报告短暂泄露 / 状态语义不一致 / 安全验收失败
- **建议改法和验证点**: 在文件读取和 checksum 验证完成前，保持对 sample/report current row 的 PostgreSQL row lock（下载用 `FOR KEY SHARE`/`FOR SHARE`，撤销用现有 `FOR UPDATE`）；响应字节已安全取回后再提交。增加两个并发测试：下载先持锁时 withdrawal 等待；withdrawal 先提交时 download 返回 unavailable。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-003-未修复-中-Slice 与验证命令仍过于宽泛
- **位置**: “Implementation slices”“Verification matrix”
- **问题类型**: 切片过粗 / 不可直接实施 / 测试缺口
- **当前写法**: expected files 使用目录级概述，没有列出精确 public types/call paths/error mapping；验证只列 suite 类别，没有可运行命令和每个 slice 的 stop condition。
- **反例/失败场景**: Slice 1 可以在 HTTP 内直接读表而仍声称“状态 lookup 已完成”；Slice 2 可以把 worker API 暴露进 public seam；Slice 3 的浏览器 fixture 可以绕过真实 finalization/worker 路径。review 无法据 plan 判定 scope drift。
- **为什么有问题**: 项目已有 `laboratory.public -> workbench/http` 组装模式和固定 Compose 测试命令，计划应绑定这些事实。
- **直接证据**: `README.md` 明确列出 `docker compose --profile test run --build --rm api-test`、browser Compose 流程和模块公开入口；当前计划未引用具体命令或 endpoint-to-service call path。
- **影响**: 实施 Agent 跑偏 / 过度耦合 / review 不可验收 / 后续返工
- **建议改法和验证点**: 为各 slice 写明 allowed modules、exact call path、stable errors、migration/versioned snapshot names、验证命令/expected assertion 和停止条件；明确 browser seeding 只准备输入事实，不能直接写 READY 报告。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Special lenses

- **Architecture boundary**: laboratory ownership and shared byte-store port direction are sound, but public/worker method visibility needs to be made exact.
- **Best practice**: immutable snapshot, lease, token compare, checksum, RBAC, and audit are appropriate; the missing lock protocol and migration compatibility prevent acceptance.
- **Optimal solution**: one current row plus a database worker is the smallest credible durable design for this repository; a message broker or report-history table would add unjustified surface.
- **Overengineering**: claim leases are justified by process-death recovery; a generic job framework is correctly excluded.
- **Overcoupling**: renderer and storage remain ports behind laboratory orchestration, but directory-level slice scopes are too loose to enforce this during implementation.
