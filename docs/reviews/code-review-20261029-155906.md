### 2-未修复-[中]-序列号候选查询使用 lower，而输入和后续匹配使用 casefold，导致已有相同序列号漏警告

- **状态**: accepted-candidate，待 controller 裁决；当前 S1 缺陷。
- **入口/函数**: 同一公开校验/修订链 → `asset_import_validation_v2.validate` 的重复序列号候选查询。
- **文件(行号)**: `backend/dga/assets/asset_import_validation_v2.py:230–232,248–255`。
- **输入场景**: 正式目录已有合法文本序列号 `Straße`，新设备行提交完全相同的 `Straße`；允许的160字符文本规则没有 ASCII 限制。仅此一个设备行时，没有同批候选可补偿已有候选的遗漏。
- **实际分支**: Python `.casefold()` 把输入改成 `strasse`，传入 SQL `lower(serial_number)=ANY(:serials)`；PostgreSQL 对现有 `Straße` 的 lower 结果是 `straße`，因此现有设备根本不进入 candidates。后面的 casefold 比较无法恢复已被 SQL 排除的记录。
- **预期行为**: 完全相同的已有序列号必须提示该设备及上下文，并要求明确确认另一物理实体；无论是否含非 ASCII 字符，都不能静默漏掉。
- **实际行为**: 该已有设备没有 duplicate_serial warning，没有正式ID/系统编号/位置候选，预览错误地表示无需这一确认。S1 暂无正式写入，但预览已违反当前交付契约；未来 S2 不能依赖这个结果作为安全确认依据。
- **直接证据**: 查询参数在:230 由 casefold 产生，:232 消费它作为 lower 的比较值；只有 candidates 或 others 非空才在:253–255 发出 warning。隔离 PostgreSQL18550 READ ONLY 查询实际返回 `lower('Straße')='straße'`，且与 `ARRAY['strasse']` 的匹配为 False。此结论是同一路径静态证明加真实 SQL 语义核实，未声称已经建立/提交Unicode正式资产的公共写入重现。
- **影响**: 需要消歧的正式资产在用户审查时消失，相同实体的再次录入缺少必需的物理确认。
- **建议改法和验证点**: 在 SQL 候选筛选、批内分组和最终比较间采用一致且明确的大小写规范；保留任意合法文本，不新增未经批准的 ASCII 限制。公开门面测试准备含 `ß` 的已有资产并导入相同序列号及大小写变体，断言已有候选和具体 warning，同时保留现有 ASCII 与同批重复测试。
- **修复风险（低/中/高）**: 低至中；必须避免只修最终比较而继续在 SQL 中漏候选，或引入与旧规则不同的身份合并语义。
- **严重程度（低/中/高/严重）**: 中（P2）。
