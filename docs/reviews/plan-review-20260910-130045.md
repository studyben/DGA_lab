# Issue #7 plan review

Reviewed target: `docs/work-units/issue-7/plan.md` on branch `codex/issue-7-finalization`, against Issue #7, ADR-0005, `CONTEXT.md`, `PROJECT_PLAN.md`, and the Issue #6 laboratory/public/auth implementation.

Scope reviewed: state machine, report-result selection, permissions, transaction ordering, concurrency, audit semantics, migration, public error contract, HTTP/UI behavior, slice sequencing, test seams, and non-goals.

## Assumptions tested

- All scientific-data writes and finalization can serialize through the existing oil-sample row lock.
- Existing `AuditTrail` can represent a failed finalization attempt durably and truthfully.
- A missing report-result selection can be communicated precisely through the existing public error shape.
- “All mutation APIs” is sufficiently precise when operational label-print auditing also mutates storage.
- A future warning-confirmation contract can be added without pulling Issue #14 rules into Issue #7.
- A partial unique index plus sample-row locking protects one selected active result per sample/type.

## Findings

### PR7-01-未修复-高-失败定稿审计会被记录为成功
- **位置**: “Persistence, audit, and concurrency” failed-validation paragraph
- **问题类型**: 契约缺失 / observability / 最佳实践偏离
- **当前写法**: A separate transaction calls the existing `AuditTrail` to append `LAB_TESTING_FINALIZATION_FAILED`.
- **反例/失败场景**: `AuditTrail.append` hard-codes `audit_logs.result='SUCCESS'`; a rejected finalization would therefore appear as a successful audit result whose action name happens to contain “FAILED”.
- **为什么有问题**: Issue #7 explicitly requires failed validation to be audited. Audit consumers rely on the result column established by Issue #3; encoding outcome in an action-code name creates contradictory records and breaks reliable filtering.
- **直接证据**: `backend/dga/shared/auth/public.py` `AuditTrail.append` always calls `_append_audit(... result='SUCCESS')`.
- **影响**: Misleading compliance history and future reporting; acceptance cannot truthfully assert a failed result.
- **建议改法和验证点**: Plan a minimal shared audit capability for an explicit `FAILURE` result (without laboratory semantics), use a neutral finalization-attempt action code, and assert action/result/entity through the public audit query after a rejected command.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR7-02-未修复-高-缺失检测类型无法穿过现有错误契约
- **位置**: report-result finalization validation and HTTP adapter sections
- **问题类型**: 公开契约缺失 / 不可直接实施
- **当前写法**: Finalization returns `report_result_selection_required` “with the missing test-type codes”, while HTTP is said to use the existing error handler.
- **反例/失败场景**: The current `LaboratoryError` carries only `code` and `status`, and the handler serializes only `{code}`. An implementation following the current plan must either lose the missing types or invent an undocumented response shape during coding.
- **为什么有问题**: The Issue acceptance requires telling the user exactly what is missing. A generic error cannot satisfy the server/UI contract deterministically.
- **直接证据**: `backend/dga/laboratory/errors.py` has no details; `backend/dga/main.py` returns only `{'code': error.code}`.
- **影响**: User-visible acceptance failure or public-contract drift introduced without review.
- **建议改法和验证点**: Specify a backward-compatible optional sanitized details mapping on `LaboratoryError`, serialize it only when present, define `{test_types: [...]}` for this error, and test both public exception data and HTTP JSON.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR7-03-未修复-中-定稿锁定范围把操作性打印与检测数据变更混为一谈
- **位置**: state machine says “every existing mutation command”; UI/non-goals omit label printing
- **问题类型**: 范围漂移 / open question 未收敛
- **当前写法**: All existing mutation commands reject after finalization.
- **反例/失败场景**: `record_label_print` is an existing mutation that only records a print audit. ADR-0005 locks sample basics, tests, and result selections—not label reprinting. Treating it as locked silently removes an established workbench operation; leaving it allowed contradicts the written plan.
- **为什么有问题**: The plan is not code-generation-ready about a currently implemented public command.
- **直接证据**: `SampleRegistry.record_label_print` mutates audit storage; ADR-0005 enumerates the scientific record being locked.
- **影响**: Scope ambiguity, accidental regression, or review disagreement over “all mutation APIs”.
- **建议改法和验证点**: Define the locked surface as scientific-record mutations: sample basics, tests, attachments through test mutation, and report selection. Explicitly keep label-print recording allowed after finalization and test it, because it does not alter the finalized report dataset.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### PR7-04-未修复-中-QA warning seam is referenced but not specified
- **位置**: warning contract and S2 fake-assessment test
- **问题类型**: 架构边界 / 过度设计 / 不可直接实施
- **当前写法**: The workbench exposes warnings, finalize accepts acknowledgements, and S2 injects a fake warning at a “narrow assessment seam”, but no owner/interface or evaluation timing is defined.
- **反例/失败场景**: One implementation may put QA rules directly in laboratory; another may create a generic provider framework; a third may compute warnings before acquiring the sample lock, allowing stale acknowledgement.
- **为什么有问题**: The goal needs warning confirmation semantics while formal rules stay out of scope. Leaving the seam implicit forces architectural design during implementation and risks coupling laboratory to future condition-analysis internals.
- **直接证据**: ADR-0004 says condition analysis consumes finalized laboratory results and must not modify laboratory records; Issue #14 owns formal QA/QC.
- **影响**: Overengineering, ownership drift, or stale-warning finalization.
- **建议改法和验证点**: Specify a laboratory-owned minimal callable/protocol passed to `LaboratoryWorkbench`, evaluated inside the sample lock from immutable candidate test records and returning stable warning codes only. Default returns none. It must not import condition-analysis. Test acknowledgement with a fake callable and defer all real rules.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

## Architecture and solution lenses

- **Architecture boundary**: selection/finalization remain laboratory-owned; no asset or condition-analysis writes are introduced. The warning seam needs explicit dependency direction before pass.
- **Best practice**: sample-row serialization and a partial unique index are complementary and appropriate; truthful audit outcome and structured stable errors are missing.
- **Optimal solution**: one additional boolean and one laboratory event table are smaller and safer than adding report entities or per-test state. No evidence supports a separate finalization module/service.
- **Overengineering**: a generic rules engine is not warranted; only a narrow warning-code callback is justified to satisfy the current confirmation behavior.
- **Overcoupling**: tests remain at the public application seam with real PostgreSQL. The proposed separate failure-audit transaction is acceptable once it uses an honest result field.
