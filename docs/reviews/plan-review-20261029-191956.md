## Findings

### 1-未修复-[高]-NULL-token旧定稿记录将阻断整个设备乃至全局报警读取

- **Status**: accepted-candidate; controller adjudication required.
- **位置**: plan §6 table line128; §7 lines133–137, especially line135; §10 legacy matrix line227; negative-fixture cases in §5 and S2 acceptance need to distinguish this state.
- **问题类型**: 兼容契约缺失 / 非最优方案 / 可用性回归 / 测试缺口。
- **当前写法**: `FINALIZED associated candidate ... with NULL token/missing/invalid fact -> existing trend_snapshot_unavailable503, never empty/partial success`；先用LEFT JOIN保留候选，再把NULL token与缺失/损坏当前事实并列为全查询失败。
- **反例/失败场景**: 数据库存在一条0006时代已定稿、在0007升级后仍`testing_finalization_token=NULL`的正式变压器油样。该物理变压器另有一条后来合法定稿、token和快照完整的油样。升级0033后，旧条目按计划不被回填事实，但S2读路径将它纳入候选并503，使另一条有效结果也不可读。AlarmCenter会一次读所有资产，因此任一资产上的此类旧记录可使整个报警页刷新失败，尽管以前该条目只是被排除、不构成有效测量。
- **为什么有问题**: #51要求保留旧结果读取及三分析模块现有语义，冻结D10只提供身份合格、当前token匹配的采用结果。NULL token从来没有匹配有效token；它与“已经声明当前非空token、但相应事实缺失/损坏”不同。将原本不合格的旧条目变为所有合格事实的故障依赖，无助于防止数据伪造，却增加跨记录和跨资产耦合。单油样仍可以明确显示需要核对，不必让无关合格资料不可用。
- **直接证据**:
  - `backend/migrations/versions/0006_laboratory_finalization.py`建立FINALIZED与finalizer/time约束，当时没有token。
  - `backend/migrations/versions/0007_laboratory_reports.py:18–19`只`ADD COLUMN testing_finalization_token UUID`，没有回填或禁止旧FINALIZED/NULL token；这是可合法升级得到的保留状态。
  - `backend/dga/laboratory/trends.py:129–137`现有`JOIN ... r.finalization_token=s.testing_finalization_token`不可能匹配NULL，因而旧条目被排除；对真正选中的坏快照才由后续解析抛503。
  - `backend/dga/laboratory/reports.py:104–105`与`backend/tests/test_laboratory_reports.py:202–223`显式保留该条目的`refinalization_required`状态；它不是有效事实或全局数据源失败的证明。
  - `backend/dga/condition_analysis/alarm_inputs.py:9–11`将`assets.alarm_assets`的全部资产ID送给一次`finalized_measurements_for_assets`；`alarms.py:69–74`没有逐条隔离NULL token旧样品错误，因此计划新增503会中断整个刷新。
- **影响**: 升级后设备趋势/健康无法读取其他合法结果；单条旧记录可阻断全局报警页。必须先逐个撤回/重做旧样品才能恢复既有功能，违反兼容准备切片目标。
- **建议改法和验证点**:
  1. 明确qualification先排除NULL token，保留当前SQL等值JOIN原有的“不合格旧记录不产生点”语义；不要生成token、事实或来源补值。
  2. `get_current_finalization`仍可对该油样返回`UNAVAILABLE/missing_finalization_token`，报告仍`refinalization_required`；诊断留在单条目。
  3. 对已合格的非空当前token候选缺失/损坏事实继续显式503、不返回部分成功；不要以本修复为由吞掉真正的损坏快照。
  4. 在真实隔离PG migration/公开接口测试中安排合法旧NULL token条目与另一条合法定稿记录，验证升级后Trends/Health/Alarm继续读合法点；单条目诊断保持，旧条目本身不产生测量。另保留非空token坏/缺事实的503用例。这样证明边界，而不是把当前NULL token排除改写成503测试。
  5. 同步计划表格、错误矩阵和负fixture说明，避免实施Agent执行互相矛盾的预期。无需产品重新访谈或额外基础设施。
- **修复风险（低/中/高）**: 低；这是读候选资格及精确测试预期的有限调整，无需重构事实存储/报告生命周期。
- **严重程度（低/中/高/严重）**: 高。
