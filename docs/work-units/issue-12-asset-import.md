## Executable contract and implementation decisions

- Fixed `.xlsx` template v1, worksheet `Assets`, one initial/current relationship per new asset. Required headers: `record_key`, `serial_number`, `material_number`, `product_line`, `machine_type`, `status`, `location_kind`, `effective_at`. Optional: `customer_id`, `site_id`, `parent_record_key`, `power_mw`, `energy_mwh`, `equipment_name`, `tag_number`, `commissioning_date`, `battery_manufacturer`. No asset-ID/update columns, no historical end dates. Parent keys refer to this batch only; importing into an existing parent is not part of this initial contract (use the existing controlled move after creation at repair center).
- System generates UUID and `AST-<full UUID hex>` numbers. Never derive identity from serial or record key. Material determines model and legacy asset type; the supplied machine_type must be compatible (TRANSFORMER only for transformer material, nontransformer kinds for WHOLE_UNIT). PV kinds: INVERTER_UNIT/INVERTER/TRANSFORMER; ESS kinds: ESS_SYSTEM/PCS_UNIT/PCS/BATTERY_CABINET/TRANSFORMER.
- Workbook identifiers must be text (leading zeros preserved), numbers finite nonnegative with at most six fractional digits and within NUMERIC(16,6), UTC or explicit-offset ISO timestamps required and nonfuture, commissioning_date ISO YYYY-MM-DD. All text length constraints match schema. Reject formulas, external links, macros, unknown/duplicate headers, wrong worksheet, invalid archive, encrypted entries, oversized content; no formula evaluation. Max compressed input 2 MiB, expanded archive 10 MiB, 100 ZIP members, 500 asset rows, 10000 cells, 1000 characters per cell. Empty file/sheet is an error, not a success.
- SITE requires explicit customer_id/site_id with verified ownership and product line, root type INVERTER_UNIT/ESS_SYSTEM and IN_SERVICE. PARENT requires a valid batch key, no site/customer fields, IN_SERVICE, matching line, parent effective_at <= child effective_at, connected SITE or REPAIR_CENTER ancestry, maximum 99 levels. REPAIR_CENTER requires no parent/site/customer and status SPARE/UNDER_REPAIR/RETIRED. Site/parent relationship is open-ended; imported historical relationship sequences are out of scope. No existing parent or asset writes.
- New `asset_materials` catalog is an additive, asset-owned table (material_number primary key, model, asset_type). Migration backfills only exact, unambiguous nonblank legacy material/model/type groups. Conflicting or incomplete legacy mappings are excluded, not guessed or overwritten. Existing assets are not changed and no new FK is forced onto legacy rows. Reference workbook includes available catalog/site/customer values. Empty/unmapped master data blocks the affected row and directs user to administrator; new master-data CRUD screens are out of scope.
- `AssetImports` is the public asset application interface: `template(actor)`, `submit(actor, filename, content)`, `get(actor, batch_id)`, `list_batches(actor)`, `publish(actor, batch_id, validation_revision, acknowledge_warnings)`, plus trusted worker `validate_next()`. It owns both staging and formal batch creation. No orchestrator obtains a SQL connection or calls independently committing lifecycle commands. HTTP/frontend use only this public seam. Separate internal workbook/validation helpers stay private.
- Dedicated `assets.import` permission granted to system_admin only; template, batches, source metadata, upload, revalidation and publication all require it. Worker is a trusted operator, not an unauthenticated HTTP route. HTTP mutations require existing Origin/CSRF checks. Missing batch 404, stale revision 409, invalid transport 422/413, storage failure 503.
- Add migration `0013_asset_import`: material catalog and import batch table with UUID, filename, SHA256, object key, byte size, source rows JSONB, row diagnostics/results JSONB, state STAGED/VALIDATED/FAILED/PUBLISHED, validation revision, submitted/published actors/timestamps, summary and safe failure code. Batch stores source and audit facts; retained source lives in S3 via FileStore. Source upload failure leaves no publishable batch. DB failure after successful PUT attempts object cleanup; failed cleanup logs only object key (no file contents). No claim of a cross-system atomic transaction. Retention cleanup policy remains deployment operations in #20; never delete published source files.
- State: submit persists STAGED after bounded parsing and source PUT (malformed workbook persists FAILED + file-level diagnostic); worker locks one STAGED batch with SKIP LOCKED, validates and commits VALIDATED even with row errors. Crash rolls back its claim so another worker can retry; unexpected validation failure stores FAILED with sanitized message. Corrected file creates a new retained batch, never mutates old input. Batch list permits recovery after browser reload. A STAGED batch cannot publish. Validation uses live catalog/sites/assets and counts valid/warning/error rows (error takes precedence), plus issue counts; each issue includes row, field, severity, actionable message.
- Publish is the public asset creation command. Under existing graph advisory lock 110011 and batch FOR UPDATE, revalidate against live data; changed validation/normalized facts advance revision, persist new preview and return without creating assets. User must inspect and acknowledge the current revision. Error rows always block. Warnings require explicit acknowledgement. All new formal assets and installation relationships, row result IDs, PUBLISHED state, actor/timestamp and audit append commit together. Any insertion failure rolls back the entire command, leaving previous preview retryable; the HTTP error never claims completion. Already PUBLISHED returns its existing result even for duplicate/concurrent requests. No event is appended to existing assets. Publication uses bound SQL/executemany, max 500 rows; no parser/HTTP input is interpolated into SQL.
- Upload HTTP uses raw XLSX body with encoded filename query (no new multipart parser); bounded stream read before threadpool call. Routes `/api/assets/imports/template`, `/api/assets/imports`, `/api/assets/imports/{id}`, `.../{id}/publish`; list GET, submit POST. Responses no-store. Internal worker command `python -m dga.assets.import_worker`, wired into local compose, validates STAGED batches; no Redis/generic broker. UI polls only pending batch, displays error or delayed-worker hint, never treats request timeout as publication failure; reload batch to reconcile.

## Original design rationale

1. Import-owned Excel contract/template + resource limits, staging persistence and row diagnostics; minimal asset-owned master-data support. Source object failure cannot create a publishable batch. Errors include sheet/row/field/actionable reason. Keep invalid duplicate keys as diagnosable rows rather than failing a uniqueness constraint during staging.
2. Public asset creation/batch application command in a single transaction. Serialize graph writes with existing lock, lock batch, revalidate live master data at publish time, require warning acknowledgement for the current validation revision, audit batch and results atomically. Rollback on any row failure, no connection/SQL crossing module boundaries. A failed attempt remains inspectable and retryable under an explicit state contract.
3. Upload/preview/corrected-file revalidation/publish UI, permissions+CSRF, load/error/empty/pending states; show imported asset identities and links only after commit.

No speculative generic import framework. Allowed files: asset module, additive migrations, shared file/background ports only when required, composition root, asset frontend, tests and issue-specific docs. Public contracts, template columns, batch state transitions, permission names, file limits, retry and source retention details must be explicit in the accepted plan before implementation.
