Format is exactly two nonempty rows: header version,format; values 1,LABORATORY. No other sheets or hidden alternate business columns. Header order may vary; the full exact column set below must be present once, even when optional values are blank; no duplicate/unknown/blank header. Instructions contain documentation, not imported rows. Template gives text number format to identifiers/dates and all written strings data_type='s'.

GET template format=XLSX returns blank XLSX; example=true returns an explicitly-labelled synthetic complete/unresolved example with no real method/asset IDs or claimed valid science. CSV_PAIR returns a ZIP download containing samples.csv, tests.csv and UTF-8 instructions.json; this ZIP is a download package, never an upload format. instructions.json states laboratory format1, file roles, columns, limits and fictitious examples. ## 11. State machines, operations and unknown COMMIT

Orthogonal state:
- business_state is always STAGED; submitted/finalized/report counts are0 and never labelled complete business work.
- manifest_state and validation readiness derive only from the selected active RECEIVED working roles with confirmed size/SHA metadata; XLSX exactlyWORKBOOK, CSV_PAIR exactlySAMPLES+TESTS, no cross-format active selection. Inactive historical PENDING/RETRYABLE files remain preserved receipt history, never a readiness prerequisite.
- validation NOT_REQUESTED->QUEUED->RUNNING->COMPLETE or FAILED; revision changes reset to NOT_REQUESTED, clear current validated_revision/current job and fence old job SUPERSEDED. COMPLETE with errors is “待核对”; COMPLETE without errors is “已校验（仅暂存）”. No “已正式导入/可发布”.
- progress phase/processed/total and technical failure_code separate from row issues. No published/partially-submitted state in this unit.
- raw file receipt PENDING->RECEIVED or RETRYABLE; RETRYABLE->PENDING on exact original-actor/original-intent retry. Only RECEIVED may be active/downloaded. Pending/retryable history can coexist indefinitely with a complete working manifest. A different current lab writer may upload a replacement under their own intent in the same batch and choose that confirmed input, without cancelling/deleting/replaying the old operation. Successful receipt still increments the existing revision and invalidates prior validation even when it is retained inactive; reservation/retryable history alone does not make another complete manifest unready.

Lock order for facade mutations: current identity shared guard30003 -> per-actor/key operation advisory lock (module-specific hash namespace, e.g.pg_advisory_xact_lock(520052,hashtext(actorUUID+key))) -> batch FOR UPDATE -> sorted candidate name locks -> source rows in UUID order -> rows/files/job in UUID order -> audit. Source candidate query must not acquire a conflicting batch lock from another transaction. No asset graph write lock or formal sample lock. Source candidate-name advisory locks(namespace520053) follow batch lock and sort by name_key before source UUID locks; that serializes NEW candidate checks without unique-name upsert. Catalog read uses identity->configuration140014 in a separate snapshot transaction, not nested after a batch lock. Worker claim/completion use identity->batch->job in the same order; only short progress updates lock job alone and never then acquire identity/batch.

CREATE/REVISE/VALIDATE write their state plus immutable operation result and success audit in one DB transaction. Request digest is SHA256(canonical JSON with exact values, sort_keys, UTF8, no float/NaN); action/version/batch are included, not just user text. Existing actor+key with different action/digest returns409. Replays return the frozen original result/applied_revision; they never relabel old refreshed/queued effects based on later current batch state. Same content/new key is a new explicit operation, not implicit duplicate business data. A recognized business rejection after digest binding (stale revision/candidate conflict) is persisted as REJECTED with safe status/code/details and failure audit in a successful technical transaction; return that error after committing the rejection. Exact replay returns the same rejection, not a new mutation. Invalid request structure before digest binding can return422 without an operation. DB/COMMIT uncertainty is never converted to REJECTED by a catch block.

File receipt has an intentionally separate durable reservation because FileStore is not a distributed transaction:
1. Read bounded content/validate filename-role-MIME, compute actual length/SHA. Transaction currentauth+op lock+batch: create PENDING RECEIVE operation and PENDING file with deterministic object key lab-imports/{batch_id}/{file_id}/source (no filename in key), digest, requested actor snapshot and60s upload token/lease. Commit reservation before provider call; if reservation COMMIT outcome is unknown,503 and query original key first, no provider call based on an unproven reservation.
2. Claiming the same pending key while its lease is valid returns202/retry-after; no second write. Expired lease or RETRYABLE state can be reclaimed only with identical digest; new token. Put occurs outside DB transaction. The unique file ID/key and same digest make a late identical writer harmless; no changed-content overwrite.
3. On put success, transaction currentauth+op+batch+file checks token/state. If still current, mark RECEIVED, activate only if role slot empty, increment revision once, invalidate validation, complete immutable FILE_RECEIVED result and audit. If the role slot has already been occupied by a chosen RECEIVED file, any late old receipt stays inactive and never replaces that active selection, even when the old reservation predated it. Successful late receipt still increments the existing manifest-history revision, supersedes the prior job/clears current validation and leaves any last result explicitly stale; that invalidation does not require adopting the late file. Active CSV byte total<=20MiB checked. PENDING record is never “file received”.
4. Definite provider failure records safe RETRYABLE status/error under its token and returns503; a put may have written before losing response, so retain object and key. Exact retry may put identical bytes again. Current grant revocation prevents final receipt success; operation remains recoverable status without granting formal write.
5. Lost final COMMIT response: never delete/re-mark failed blindly, never change intent key; original operation query may reveal COMPLETED. If DB unavailable leave uncertainty, not404-as-failure. A stale upload token cannot increment revision or complete twice. No auto object cleanup in #52.

Receipt reserve/retry metadata updates are system technical state, not a new formal action. Unknown receipt bytes, original actor-private operation and its reservation/object/recovery metadata are retained for recovery. An abandoned inactive receipt does not prevent another current lab writer's own upload/active selection and same-batch continuation; basic replacement continuation is required here, not deferred to#60. Broader orphan reconciliation remains#60. Source lab allocations are transactional metadata, included in CREATE/REVISE idempotent result; there is no name upsert.

Audit action enums: LAB_IMPORT_CREATED, LAB_IMPORT_FILE_RESERVED, LAB_IMPORT_FILE_RECEIVED, LAB_IMPORT_FILE_FAILED, LAB_IMPORT_REVISED, LAB_IMPORT_VALIDATION_QUEUED, LAB_IMPORT_VALIDATION_COMPLETED, LAB_IMPORT_VALIDATION_FAILED, LAB_IMPORT_SOURCE_DOWNLOADED. Details contain batch/revision/op/file/source decisions/changed values and executor worker_id when applicable. Actual requester remains audit actor; source_analyst stays source evidence and is never audit actor. Audit failure rolls back the corresponding DB success marker; a known-stored object is retained, not reported received without commit.

## 14. Implementation slices: three coherent vertical capabilities

There is no fixed slice-count limit. Three slices are chosen because they separate the evidence-commit/storage risk, bounded asynchronous scientific parsing risk, and human-review concurrency/recovery risk. Each includes facade/HTTP/UI/real PostgreSQL tests for its user behavior; none is a database/frontend/backend-only phase. Four or more would split one validator protocol into intentionally incomplete temporal/numeric stages and duplicate gate overhead; two would combine storage reservation, parser/lease and review races into one oversized pass. One implement + one independent code review is the intended scale per slice; no skipping gates or all-slice implementation in one dispatch.
